# TfNSW Proxy Worker

`cityrail.exe` runs from GitHub Pages, so it cannot call TfNSW APIs directly:
the browser would expose the API key and TfNSW does not answer the required
CORS preflight from a static origin.

Deploy `tfnsw-proxy.js` as a Cloudflare Worker and set these variables:

- `TFNSW_API_KEY`: Cloudflare secret containing your TfNSW Open Data API key.
- `ALLOWED_ORIGIN`: GitHub Pages origin, or `*` if you do not want to restrict browser origins.

The app expects the Worker base URL in the CityRail live panel. The Worker
exposes:

- `GET /api/tfnsw/stop-finder?query=Central`
- `GET /api/tfnsw/departures?stopId=10101100&date=20260606&time=1530&limit=12`
- `GET /api/tfnsw/gtfs-trip-stops?tripId=3001.nsw-2-T1-W.1.TA.4823.sj2`
- `GET /api/tfnsw/trip-details?originId=10101100&destinationId=10101140&date=20260606&time=1530`

For reliable intermediate stop lookup, the browser first uses the static GTFS
index generated by `.github/workflows/update-cityrail-gtfs-index.yml`. The
Worker GTFS route is only a fallback because parsing GTFS during a request can
hit Worker CPU limits on cold starts.

Example deployment commands:

```sh
wrangler secret put TFNSW_API_KEY
wrangler deploy workers/tfnsw-proxy.js
```
